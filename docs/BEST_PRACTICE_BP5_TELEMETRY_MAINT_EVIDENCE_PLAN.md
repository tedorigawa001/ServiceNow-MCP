実行時に別途確認する条件：

## 3. 担当者に確認してもらう項目

各項目は`confirmed / not_observed / inaccessible / unknown`で回答し、観測した範囲と証拠の有無を添える。
`not_observed`は指定期間・可視範囲で見つからない意味で、プラットフォーム全体での不存在ではない。

| ID | 担当者が内部で確認する内容 | 提出してよい結果（実値を除く） |
|---|---|---|
| C01 | 対象インスタンス、調査主体の既存maint権限/担当範囲、設定表の実際のread可否 | 接続先一致yes/no/unknown、権限確認yes/no、read可否。個人名やログイン情報は不要 |
| C02 | `APIKeyBuilder`→`APIConfigLookupService`が使う設定識別名と検索順。サービス名付き検索と接頭辞除去後の検索 | 使用経路の確認範囲、各検索の一致件数、候補の重複有無。識別にはCFG-A等の仮名を使用 |
| C03 | 対象設定の現在値と、既存履歴で確認できる実行時点の対応。複数一致なら選択根拠 | 対応confirmed/unknown、同値/変更あり/履歴不足、件数と仮名。先頭行を確定したとは推測しない |
| C04 | `api_endpoint`の有無、形式、内部設計上の参照先との整合。`method`の有無/既定値の適用 | present/empty/unknown、形式valid/invalid/unknown、HTTPメソッド、既定値使用yes/no/unknown。ホスト・パス・queryの実値は提出しない |

| C06 | C05と標準の`getValue(...) || {}`・`JSON.parse(...)`・catch後`{}`の関係 | 空値代替による解析失敗と整合/非整合/unknown、空ヘッダー続行の確認可否。最終原因とは断定しない |

| E04 | 元の例外と、`this.logger`参照時の二次例外を区別できる既存スタックがあるか | first/secondary/unknown、標準クラス・メソッド・行番号、版。logger未初期化は別項目として判定 |

`api_key`はこの表では設定識別名。認証用APIキーと混同しない。
設定識別名も秘密の可能性があれば提出せず仮名化する。資格情報や認証ヘッダーの内容・ハッシュ・長さ・
有効性検証結果は求めない。HTTPメソッドが分かっても、送信された証明にはしない。

## 4. 秘密を含まない証拠の取得・提出手順（実施前の案）

1. **範囲を固定する。** 読み取り承認後、対象・主体の可視範囲・時刻表示のタイムゾーン・ログ保持/欠損を記録する。
   過去の観測時刻はUI表示2026-10-17 21:48:55–21:51:45でタイムゾーン未検証。
   これをJST/UTCと決め付けず、まず対応を確認してから固定した開始/終了範囲を決める。
   再現に依存するToday条件をそのまま再利用しない。対応不能なら時刻不確定と記録する。
2. **設定をその権限領域内で確認する。** C01–C07を必要最小限だけ参照し、外部へは分類・件数のみ転記する。
   ヘッダー等の実値のコピー/ファイル化は避ける。JSONの妥当性を既存の承認済み手段で確認できない場合は
   `not_checked`とする。新規の検証スクリプトやツール、オンラインvalidatorを導入/実行しない。
3. **既存ログを限定して読む。** 既知のクラス/エラー種別と固定時間帯で絞り、全ページ数・確認行数・
   不可視/保持の限界を記録する。既存スタック等が正当に読める場合だけE01–E04を照合する。
   token/credential表、通信payload/headersの一括取得や新規ログ有効化には進まない。
4. **相関を明示する。** 内部で比較できる既存のrequest/transaction識別子は提出票ではREQ-A等に置換し、
   元IDやそのハッシュは提出しない。対応表は必要な場合のみ既存の承認済み非公開領域で管理する。
   同じ秒だけなら`time_only`、明示した要求単位の証拠があれば`request_linked`、なければ`unlinked`とする。
   時刻一致だけで因果関係や要求件数を確定しない。
5. **白リスト方式で証拠票を作る。** §5の欄だけを新規に転記し、生ログ・JSON/XML・HAR・スクリーンショット・
   設定exportを添付しない。スタックは標準クラス/メソッド/行番号だけを抜き、引数・動的文字列を除く。
   エラーメッセージ全文ではなく、既知の定型分類と短い説明にする。
6. **提出前に秘密確認する。** 作成者と、閲覧を許可された確認者が可能なら別々に確認する。
   認証値、cookie、client ID、ユーザー/メール、URL/query、ヘッダー名/値、本文、内部ホスト/アドレス、
   未置換IDや動的スタック引数がないことを確認する。自動の文字列置換だけで安全とは判断しない。
   判定不能な欄は値を出さず`withheld`とする。提出先/確認者が未承認なら提出しない。
7. **結論を分離する。** 設定の解析結果、元の通信段階、loggerの二次エラー、PDI提供条件を別々に回答する。
   証拠不足はunknownのまま提出し、解消のための設定変更や通信試験は別計画・別承認へ送る。

原本は元のシステム/既存の保管方針の下に残し、新たなローカル機密コピーを作ることを前提にしない。
既存ログを削除・延長保存・移送する操作も本手順には含めない。
