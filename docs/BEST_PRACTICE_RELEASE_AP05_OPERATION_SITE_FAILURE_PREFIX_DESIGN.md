## 1 消費・到達・確認は同じ状態ではない

記録のキーは `plan版／候補pin／系列／slot_id（SLまたはMT）／attempt／subcheck_id／site_ref／対象ID`。site_refは親SPと下表の小文字suffixを結ぶ。MTが参照するSLは判定の出典であり、課金・所有を元SLに合算しない。固定predicateと期待理由はmanifestから引用し、運転中に選び直さない。未生成の成果物digestや未受領handleは別欄で保持し、値がないことを未到達にしない。

| 軸 | 固定する事実・確定点 | 代用しないもの |
|---|---|---|
| 操作枠の消費 | 同owner・予算・phaseを確認後、外部呼出し又は不可逆操作の**直前**に同siteの試行を消費する。失敗・throw・無応答でも戻さない。通過bytesは既知量と未計数を区別し、実I/Oの不明量をゼロにしない | 枠予約だけで実消費とはしない。一度限りの消費は操作の成功・実体生成を証明しない |
| 到達 | 入場前の拒否や、生成受付を閉じた正規の履歴で、呼出しなしと確認できるsiteだけを未到達とする。試行先行記録の後で停止した場合は、実呼出しまで到達したかを別欄に置く | ログなし・handleなし・記録自体の不達では、未到達または消費ゼロを認定しない |
| 結果確認 | 同identityの成功・固定失敗・確認済み未生成を分ける。通知欠落・別世代・不明な時刻は未確認。保全側への受理は退出・stdio終端・削除完了のいずれも代替しない | code 0、停止要求、ready／finish、片側EOF、空欄を他軸の完了にしない |
| 保持責務 | 生成試行、実体受領、借用、上位受理、操作・空確認を別記録にする。参照が残る責務の初期owner／現在owner／処理資格と、先行理由を保持 | 失敗の終端を封印しても、資源の解放や責務の消滅にはしない |

したがって「操作枠＝消費済み／呼出し＝未確認／終了＝未確認」は併存する。消費記録そのものが不明なら、当該枠を未確認として再利用せず、初期の保全枠から最後に確認できたprefixを照会する。保全登録が確認できない段階では後続I/O・起動を行わず、仮の受理票も作らない。保持容量は数値未承認で、記録や資源を安全に保持できない案は起動しない。

## 4 配賦の照合と、後続へ渡す未確定欄

通常slotでは入場・実行・通常終端・slot専有物の受理／解放まで `W_i`。系列の停止点で通常入場を閉じ、未完了責務と共有物の最終処理だけを、系列で一度の `R_cleanup` に渡す。各SPの実操作IDを基準に、Wで消費済みの試行や確定済み証拠をRで払い直さない。一方、Wで始めた作業が止まるまでの処理と、Rで必要な残りの観測・同票照会・保全は別費目。待受の連続区間も引継ぎ点で分け、同じ時間を両枠に重ねて計上せず、相互の余りを借りない。親の `t_i + W_i < D_obs`、各 `Rk` の絶対cutoffと `D_end` を変更しない。

次の台帳欄に、`site_ref／実site相対位置／entry・fixture／対象同一性／L行`、`試行消費の確定点／到達証拠／結果根拠／未到達suffix`、`SR参照／最後に確定したsite／残存対象・現owner世代／受理票照合／次に許す処理`、`W・R別の回数・件数・通過／保持bytes・待受根拠` を持たせる。具体のrevision・digest・実site、操作係数／上限、観測手段と独立性、保全先・方式・権限は未確定または未承認。未知を零にしない。候補Pの起動には別承認と、全siteの根拠が必要。

将来の設計対照では、同じprefixからW/R二重課金・逆に漏れがないこと、登録不明時の起動0、PΔの差分不一致、終了通知の前後入替え、ack消失、部分削除、期限境界を独立に確認する。所定の失敗を検出したPΔでも、独立終端が足りなければ次は起動しない。ここでは対照の実行・候補検証・閉鎖条件解除を行わない。

## 5 静的確認

基準`28f574c`で、§2のSP01〜15がmanifestのsite表の範囲と一致し、各SPの費目（SP01→L01、SP02・03→L02、SP04→L03、SP05・06・08〜10→L04、SP11→L05〜07、SP12→L08、SP13〜15→L09〜11）がmanifestの対応と合うこと、構造のみのSL16・20、全MTのSP08→SP09→SP10（SP05）、SL22のSP12〜15、FP01のSR01／06がmanifestのSL01行と一致すること、FP01〜12の引継ぎ先と外側時間枠設計のR1〜R7の主題、`t_i + W_i < D_obs`・`R_cleanup` の実在を静的に照合した。本書のID12行（FP01〜12、欠番なし）が他文書のIDと衝突しないこと、表3・ローカル参照6・明示anchor0、参照先・表列数・末尾改行・差分空白を確認した。製品・試験・設定の差分はなく、実行・build／pack・変異・process／保全操作は行っていない。
