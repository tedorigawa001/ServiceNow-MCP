# BP-4: 独立ケースセットによる候補品質評価

> 評価契約の追記: v0.1の適合率80%目標は、候補保持が正しい例外をFPに数えるため
> 現契約では構造的に到達できない。以下の目標・結果・CLIは初回記録として保存するが、
> v0.1の二値ゲートを検出器の品質承認・リリース判定には使用しない。
> 検出器の限界と採点契約の問題を分け、v0.2で期待結果を再設計する。

## 評価前に固定するプロトコル（2026-10-17）

BP-3エンジン（基準コミット3a2967738845fcbd1303be79c87b1c9a39e780bc）は変更せず、
新しい合成ケース48件を作成した。対象はAU-BR-001/002・AU-CL-004。
問題あり・問題なし・例外・情報不足を各12件、各規則×分類は4件ずつとする。
既存回帰テストやPDI本文のコピーではない。

ただし作問者は実装を参照済みであり、完全なブラインドholdoutでも第三者の採点でもない。
ここでの独立性は「既存回帰テストとは別の新規ケース・固定ラベル」の意味に限定する。
類似する変形ケースも含むため、48件を独立同分布の標本とは扱わない。
実案件の再現率や事故防止効果に一般化しない。人による採点承認も未実施。

[ケースセット](../tests/review/evaluation/bp4-cases.json)の初回実行前のファイルSHA-256:
`ca0aee13e9ccb66a353d14493e7074c41976f67ef8b9222679f81a0cf00451ad`

結果に合わせてコードやラベルを書き換えない。後で改善に用いた時点でこのセットは
開発用評価になるため、改善後の独立評価には未使用の追加セットと人の採点が必要。

### ラベルの意味

- problem: 根拠規則に照らし調査すべき問題がある想定。別名・間接呼び出しも含む。
- no_problem: その規則には該当しない。資産全体の安全性を保証しない。
- exception: 根拠で区別すべき適用外、または合成の外部審査条件で例外承認済み。
  setWorkflow(false)を常に許可する意味ではない。外部条件はrationaleに明記するが、
  現在のエンジンは受け取れないため、自動除外できないこと自体を限界として測る。
- insufficient: リリース・実行時点・本文等が不足/不正で判定不可。理由付き保留が正解。

根拠は[Australia台帳](BEST_PRACTICE_REGISTER_AUSTRALIA.md)の該当3規則とその根拠節。
新しい一般則を公式資料の確認なしに追加するものではない。

### 指標・事前目標

評価単位は1ケース×要求した1規則。出現回数ではなく候補の有無を数える。
閾値はcandidate以上（現在は全件candidate/low/info）。検索スコアは使わない。

問題あり12件と問題なし/例外24件の36件を二値集計する。
TP=問題ありで候補あり、FN=問題ありで候補なし、FP=問題なし/例外で候補あり、
TN=問題なし/例外で評価済みかつ候補なし。
正例の拒否/スキップはFNに含め、取りこぼしを隠さない。
負例の拒否/スキップはTNにせずnegative_abstentionsとして分離する。
評価済み率は36件中evaluatedの割合として併記する。

適合率=TP/(TP+FP)、再現率=TP/(TP+FN)。分母0はnullであり100%にしない。
情報不足12件は適合率/再現率に混ぜず、候補0件・正しい拒否/スキップ理由・
completedを主張しないことを別に検証する。

| 事前目標 | 閾値 |
|---|---|
| 候補適合率 | 80%以上 |
| 候補再現率 | 90%以上 |
| 評価済み率（問題あり/なし/例外） | 100% |
| 情報不足の適切な保留 | 100% |
| 未検証の確定指摘 | 0件 |

ここでFPは要トリアージ候補のノイズであり、「確認済み脆弱性の誤報」ではない。
特に例外は、例外条件を入力できない現契約の限界も含む。根拠承認前に
evidence_matched/path_confirmed/runtime_confirmedへ昇格させない。

### 再現方法

```bash
bdo node --import tsx scripts/bp4-evaluate.ts
bdo node --import tsx scripts/bp4-evaluate.ts --strict
bdo npm test -- tests/review
```

通常実行は評価報告を作れればexit 0。品質合格を意味しない。
--strictは品質目標未達でexit 2、入力/実行異常はexit 1。
テストの成功とquality_gate_passedを区別する。
結果はコード本文を含めず、件数・規則・ケースID・拒否/スキップ理由を出力する。
dataset_hashは検証/正規化済みケース集合のハッシュ、fixture_file_sha256は元ファイルのハッシュ。
ネットワーク・PDI・外部AI送信・コード実行は使用しない。

### 誤検知・取りこぼしと次の改善候補

| 対象ケース | 観測結果 | 原因・検討する対応 |
|---|---|---|
| P03/P04/P07/P08/P11/P12 | FN 6件 | レコード・メソッドの別名、引数経由、bind、動的プロパティを追跡しない。限定的なデータフロー解析を検討 |
| N04/N07/N08/N11 | FP 4件 | ローカル変数のシャドーイング・受信型を区別しない。字句スコープ/束縛解析を優先 |
| E01〜E04 | 候補ノイズ4件 | workflow抑止付きの例外審査情報を入力できない。抑止だけで自動除外せず、追加確認の契約を設計 |
| E09 | 採点上のFP 1件 | 現方針では非アクティブでも候補を保持しinactive_assetを付ける。候補の抑制でなく、制限の付与を採点すべき契約上の問題 |
| E10/E11 | 候補ノイズ2件 | 到達不能/未呼出し。実行可能性の確認で一部改善できるが、特に他からの呼び出し不在は追加文脈を要する |
| E12 | 候補ノイズ1件 | ローカルの同名スタブ。変数の束縛・受信型の区別で改善可能 |
| E05〜E08 | 適切な非検出4件 | 条件欄・条件ビルダー・補助レコードを本文と混同しなかった |
| I01〜I12 | 適切な保留12件 | 理由付きスキップ/拒否を維持。問題なしには数えていない |

P04のラベルは、取得したメソッドのcallによる呼び出しが対象ランタイムでも成立する
という合成上の仮定を含む。ServiceNowのホストオブジェクトでの実行は未検証であり、
人による採点で妥当性を確認する。実行後にケースを除外/改変せず、初回結果はそのまま残した。
同様に外部承認を前提とする例外ラベルも、実在する審査やPDI実行の証拠ではない。

現時点でMCP統合や違反確定へ進める品質承認はしない。
次は字句スコープと限定的な別名追跡を優先し、外部文脈が必要な例外の入力・保留方式を
別途設計する。改修時には本セットの再実行と、未使用ケースによる再評価を分離する。

## レビュー後の評価契約の訂正・次版方針（2026-10-17）

### v0.1の目標が構造的に到達できない理由

E01〜E04は、合成の外部審査では承認済みでも、その承認情報をエンジンへ渡す手段がない。
設計・台帳はsetWorkflow(false)だけで自動除外しないため、候補保持が正しい動作になる。
しかしv0.1採点はこれを必ずFPとする。正例12件をすべて検出し、他のFPをすべて解消しても
適合率は12/(12+4)=75%で、80%には届かない。
E09も「非アクティブの静的候補は保持する」という現方針を固定すれば、上限は
12/(12+5)≒70.6%となる。これは束縛解析だけでは解消しない、出力契約と採点の不整合である。

既存ケース・ラベル・集計器・結果JSON・--strictのexit 2は初回記録として変更しない。
これを使って「目標未達を解消するためworkflow抑止やinactiveを一律除外する」改修はしない。
集計器の完全オラクル合格テストは算術を確認するだけであり、正しい出力契約のまま
エンジンがこのゲートへ到達できることの証明にはならない。

### FP 12件の分離と条件付き改善試算

| 分類 | ケース | 件数 | 扱い |
|---|---|---:|---|
| 束縛・受信型の混同 | N04/N07/N08/N11/E12 | 5 | 字句スコープと受信型、currentのフィールドに対するchanges系等の形を検証 |
| 実行条件・到達可能性 | E10/E11 | 2 | 一部は解析で改善可能。全呼出し元の不在までpayloadだけで断定しない |
| 外部審査・採点契約 | E01〜E04/E09 | 5 | 承認・非アクティブの扱いは候補の単純抑制では解決しない。必要な追跡確認や制限を採点 |

上記5件の束縛/受信型FPを解消し、単純な別名追跡でP03/P08の2件を検出できたと仮定すると、
TP8/FP7/TN17/FN4、適合率8/15≒53.3%、再現率8/12≒66.7%となる。
これは実装・実測結果ではなく、改善対象のケースが想定どおり動いた場合の算術試算。
優先順位は妥当だが、この改良だけで旧ゲートを通過しないことを着手前の前提とする。

### 件数と不確実性

| 指標 | 件数 | 点推定 | 95% Wilson区間（参考） |
|---|---|---:|---|
| 候補再現率 | 6/12 | 50.0% | 25.4〜74.6% |
| 候補適合率 | 6/18 | 33.3% | 16.3〜56.3% |

正例は12件なので、1件の変化で再現率が約8.3ポイント動く。
Wilson区間はz=1.959963984540054、p=k/nとして、中心
(p+z²/(2n))/(1+z²/n)、半幅z√(p(1-p)/n+z²/(4n²))/(1+z²/n)から算出した。
ただしこのセットは意図的な層化・関連した合成ケースであり、独立な二項標本ではない。
区間は少数例の数値の幅を示す参考値に限り、実案件の母集団に対する95%保証とはしない。
分類率や信頼区間を、規則の根拠承認や違反の実機確認と混同しない。

80%/90%による品質承認はv0.1では行わず、採点契約を修正しケースを拡充した版でのみ検討する。
次版はケース数を増やすだけでなく、標本設計・人によるラベル検証・許容する不確実性・
区間をどう合格判定に使うかも実行前に定める。

### v0.2の期待結果（設計のみ・未実装）

新規の未使用ケースでv0.2を作成し、判定可能なケースの期待結果を次の3種類に分ける。
旧ケースを別名に変えるだけで独立セットとはしない。v0.1は固定した開発用/履歴評価として残す。

| 期待結果 | 正しい出力 | 採点するもの |
|---|---|---|
| candidate | 候補を出す | 対象規則の候補有無・位置・根拠 |
| clear | 候補を出さない | 誤った候補がないこと。未評価/拒否をclearにしない |
| candidate_with_followup | 候補を保持し、指定の確認項目/制限を付ける | 候補と必要なrequired_follow_up / limitationsの両方。確認済みへ誤昇格しない |

candidate_with_followupは評価側の期待分類であり、レビューJSONのverification_statusを
新しく増やすという意味ではない。E01〜E04相当では承認範囲・副作用・業務意図等の
追跡確認、E09相当ではinactive_assetの制限を採点する。外部審査情報を渡していない場合、
架空の承認済みをエンジンが推測することは要求しない。

候補有無の指標ではcandidateとcandidate_with_followupを正例として扱い、clearだけを
負例にする。別に3分類の一致率と、必要な追跡確認/制限の適合率を測る。
確認項目は必要な集合の包含で検査し、無関係な汎用注意書きだけで合格させない。
情報不足はこの3分類に押し込まず、別軸の理由付き保留として維持する。
リリース不明/不一致で候補を出さない既存の安全契約も変えない。

P04は人による採点確認の最優先とする。ServiceNowのホストオブジェクトで.callが成立するか
未検証のまま、確定した正解ラベルとして次版に流用しない。確認結果は既存ラベルを黙って
書き換えず、別の検証記録と版で扱う。今回PDIでコード実行は行っていない。

追記時に上記の数値をローカルで再計算し、既存評価テスト9件の成功によりケース/保存結果の
不変性を確認した。git diff --checkも問題なし。
新しい採点器・ケース・検出器の実装はこの追記には含めない。
