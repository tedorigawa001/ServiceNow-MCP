## 原因と修正

| 対象 | 修正 |
| --- | --- |
| サブフロー一覧 | 不在の `sys_hub_subflow` ではなく、`sys_hub_flow` に `type=subflow` を必須指定 |
| サブフロー詳細 | 名前検索も同じ型条件を使用。sys_id指定は実レコードの `type` を確認し、通常Flowや型不明を `NOT_FOUND` として拒否 |
| 通常Flowの一覧・詳細 | 同じテーブルを使うため、対称的に `type=flow` を指定・確認し、Subflowとの混在を防止 |
| 作成メタデータ | `create_subflow` は共有表に `type=subflow,active=false`、`create_flow` は `type=flow,active=false` を明示 |
| 有効化メタデータ | `publish_flow` の `type` はschema/runtimeともflow/subflowだけ許可。実レコードの型を確認してから共有表の `active` を更新。WRITE_ENABLEDガードは維持 |
| Process Automation | 不在の `pa_process` → `sys_pd_process_definition`。一覧は内部名 `name`・表示名 `label`・説明 `description`、詳細の文字列検索は内部名・表示名を対象にする |

実機の辞書とレコードから、Flow/Subflowのraw型値、PADの `name,label,description,active,status` を確認した。PADでは内部名 `task_steps_2` に対し表示名は `Task steps` であり、nameだけの検索では利用者の表示名入力を扱えなかった。

検索文字列は既存の `sanitizeLikeValue()` を使う。`active:false` はactive-only条件を解除する意味であり、inactiveだけを選ぶ変更ではない。ツール名・入力パラメーター・外側の返却形式を維持したが、`list_flows` がSubflowを含まなくなる点、`get_flow` と `get_subflow` の型違いが拒否される点は意図した挙動変更。

公式資料との照合: [Flow API](https://www.servicenow.com/docs/r/application-development/servicenow-sdk/fluent-flow-api.html) のSubflow定義先は `sys_hub_flow`、[PDAutomationProvider](https://www.servicenow.com/docs/r/ja-JP/api-reference/server-api-reference/PDAutomationProviderBothAPI.html) の定義参照先は `sys_pd_process_definition`。今回の判定は資料だけでなくPDIの辞書・raw値で確認した。
