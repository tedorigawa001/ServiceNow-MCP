## 2. 共通の判定契約案

- 単位は対象版のケース×規則。候補は人が確認すべき兆候であり、脆弱性・実行・障害の確定ではない。
- 入力には対象版（Update Set payload/現行）、匿名化コード、資産種別、scope、release、
  必要なwhen/UI/active、条件欄・依存情報と既知の欠落を含める。異なる版の証拠を合成しない。
- `candidate`：対象規則の適用が確認でき、コードに対象の挙動を示す最低限の証拠がある。
  効果・実行経路や一部受信側が未確定でも、下記カードの最低証拠を満たせば候補＋制限とする。
- `clear`：必要なコードと文脈が揃い、この規則の兆候を否定できる。文字列/コメントだけ、
  独自の同名メソッド、別レコードだけの操作等、否定した箇所と根拠を示す。
- `insufficient`：適用条件、本文、対象版等が欠け、最低証拠を満たすか決められない。
  受信側や承認資料の不明だけを機械的にこの判定へ落とさず、各カードの境界に従う。
- `not_applicable`：資産種別・BR実行種別等が明確に規則の対象外。clear/TNには含めない。
- 途中までしか読めていない、切り出しで束縛が消えた、リリースが未照合/不一致なら、
  完全な評価済み・clearとはしない。理由と未評価範囲を示す。既知の候補を隠さず、
  部分的な参考所見と全体の評価不能を分離し、正式な候補品質集計の扱いは事前登録する。
- var/const、別名、関数経由等は表記だけで意味を変えない。人が証拠を追えるかで判断し、
  現検出器の解析範囲・成功結果をgoldの根拠にしない。未解決の挙動を推測で補完しない。

各所見に匿名化版の位置、対象操作/受信側、根拠節、判断理由、欠落情報を記録する。
確認項目は未完了の確認依頼であり、付与だけで例外承認や検証状態を昇格させない。
`active=false`は候補を消さず`inactive_asset`という制限にする。未知のactiveからは生成しない。
例外承認は対象・期間・範囲が合う資料が必要。承認なしと承認不明を区別する。

## 3. AU-BR-001：現在レコードの再更新

**根拠節**：AU-SRC-001 / How business rules work → Prevent recursive business rules。
**意味**：BR内の現在レコードの明示的再更新を確認し、再帰・連鎖・不要な更新の可能性を点検する。
before/afterやworkflow抑止だけで一律の違反/安全とは決めない。
**適用**：AustraliaのBR本文。Global/Scopedとも対象。実行種別は記録するが、特定のwhenだけに限定しない。

| 判定 | 必要な証拠・境界案 |
|---|---|
| candidate | BRの実行文脈におけるcurrent、または同じ現在レコード由来と追える参照への明示的update呼び出し。呼び出し位置と由来を記録。到達経路・実際のBR再発火が未確認でも候補 |
| clear | 十分な本文/束縛情報があり該当操作がない、または同名のローカル変数/別レコードへの更新と確認できる。単なるコメント・文字列内のcurrent.updateも除く |
| insufficient | BR本文/版が欠落、または不明な参照へのupdateしかなく現在レコード由来を裏付けられない。API名updateだけでは候補にしない |
| not_applicable | 対象がBR本文ではないと確認できる |

必要な追跡証拠：入口のcurrentの束縛、別名/引数/戻り値を経由するなら対応関係、再代入、
対象版のwhen/active、関連する条件・呼出し元。現在レコードの通常のフィールド代入だけは再更新候補にしない。
明確に実行不能と否定できる操作は除くが、未提示の呼出し元や条件を「実行されない」証拠にしない。

**確認項目**：`workflow_suppression_review`（context_specific）。現在レコードの再更新と
`setWorkflow(false)`の抑止が関係する証拠があればrequired。受信側、引数の値、順序、分岐、
途中の再有効化を記録し、抑止の理由・必要性・承認範囲・失われる自動処理/監査等への影響を確認する。
これは同一関数/構文順序だけを意味上の正解にする提案ではなく、人が追える関係を対象とする。
十分な文脈で無関係/抑止なしならnot_required、関連を決められなければundetermined。
requiredでも抑止効果は未検証であり、未検証なら`workflow_suppression_relation_not_verified`を制限へ記録する。
更新後の抑止、別レコードだけの抑止、コメント中の語だけを根拠にrequiredにしない。

**人が決める点**：現在レコード由来の最小証拠、実行不能の否定証拠、複数関数/分岐での抑止関係の採点方法。

## 4. AU-BR-002：非同期BRの過去値・変更判定への依存

**根拠節**：AU-SRC-001 / How business rules work → When business rules run（Note）、
Global variables in business rules。
**意味**：非同期本文でpreviousや変更判定に依存する箇所を確認する。条件欄の評価と本文を区別する。
**適用**：AustraliaのBRで、保存値がasync_alwaysまたは旧asyncと確認された本文。
保存値の対応は既存PDI調査記録に基づく前提で、人のカード承認時に再確認する。
before/after/before_displayは本規則の非同期本文対象外。不明なwhenを非同期と推測しない。

| 判定 | 必要な証拠・境界案 |
|---|---|
| candidate | 非同期本文にBR由来のpreviousのプロパティ/値への依存、またはcurrentのフィールド由来と追えるchanges/changesTo/changesFromの利用がある。別名経由も由来の証拠を示す。存在確認のみ・ガード内参照は下記の未承認論点として分ける |
| clear | 非同期本文と束縛を確認でき、依存がない。独自ローカルprevious、独自changesメソッド、文字列/コメントだけ、条件欄にしかない変更判定は本文候補にしない |
| insufficient | when不明、本文と条件欄の区別不能、または参照のBR由来/フィールド由来を決める証拠が不足。previous/changesという名前だけでは候補にしない |
| not_applicable | 非同期以外のBR、またはBR本文でないと確認できる |

必要な証拠：対象版のwhen保存値、script/condition/filter_conditionの区別、previousの束縛、
変更判定の受信側とフィールドの由来。単なる引数宣言、存在確認、プロパティ参照、
ガード/フォールバック、try/catchを分けて記録する。参照が構文上あることと到達可能性を混同しない。

**確認項目**：`async_dependency_review`（rule_intrinsic）を候補全件でrequiredとする。
過去値を必要とする理由、null/未定義の扱い、フォールバック、互換分岐、期待する変更判定の時点、
条件欄や別の設計へ移す場合の意味の変化を確認する。項目付与は防御処理の認定・例外識別ではない。
承認済み境界で候補とした場合は、ガードがあるだけでnot_requiredにしない。
候補を認めない場合は固有項目だけを生成しない。

**人が決める点**：次の2種類を別々に承認する。双方を一律に「過去データの読み取り」と扱わない。

| 論点 | 必要な区別・承認事項 |
|---|---|
| `if (previous)`等の存在確認だけ | オブジェクトの有無の確認で、過去レコードのプロパティ読み取りではない。これ自体をレビュー候補に含めるか、clearとするかを別途決める |
| 存在確認のガード内で`previous.<field>`を参照 | asyncでpreviousを利用できないという根拠前提が成り立つなら、ガード内は到達しない。その前提・束縛・再代入を確認し、実行不能な依存設計として候補にするか、到達不能として除外するかを決める。実際に過去値を読んだとは報告しない |

when・束縛・前提を確認できない場合のinsufficientとの境界も承認する。
受信側不明のchanges系に必要な由来証拠と合わせ、未承認のまま実装の現在の動作へ採点を合わせない。

## 5. AU-CL-004：同期GlideAjaxの候補

**根拠位置**：AU-SRC-002 / Minimize server lookups → Retrieve server data using asynchronous GlideAjax
の**例コード中のコメント**（非同期呼び出しを同期呼び出しより優先する旨）。節の見出しそのものを
根拠文とはしない。このlocatorは今回のレビュー指摘に基づく訂正であり、人による原文再照合は未実施。
**意味**：クライアントの動的なサーバー照会について非同期化を検討する。
同期によるUI影響と代替の妥当性の確認は、当該コメントを踏まえた本プロジェクトの解釈・確認方針であり、
AU-SRC-002が個別のUI影響を断定しているという引用ではない。
同名メソッドだけでGlideAjax使用を確定しない。
**適用**：まずAustraliaのClient Script本文。UI Script等は実行UI/呼出し文脈を含む
別の適用承認後に拡張し、本案から自動的に対象へ加えない。

| 判定 | 必要な証拠・境界案 |
|---|---|
| candidate（受信側確認） | クライアント本文でGlideAjax由来と追える受信側のgetXMLWait呼び出しを確認。場所・由来を記録 |
| candidate（受信側不明） | 完全な呼び出し式のgetXMLWaitを確認でき、受信側が引数等で不明、かつ独自同名実装と確定する証拠がない。同期GlideAjaxと断定せず候補＋受信側不明の制限とする、という提案 |
| clear | 十分な本文/文脈で該当呼び出しなし、非同期APIのみ、または独自の同名メソッドと確認できる。文字列/コメントだけも除く |
| insufficient | 本文/対象版/UI文脈が不足、式が欠けて呼び出しか判断不能、動的なメソッド名が解決不能で具体的な対象呼び出しを裏付けられない |
| not_applicable | Client Scriptでない等、今回承認する対象範囲外と確認できる |

**境界の選択案**：API名が一致する完全な呼び出しがあれば受信側不明でも候補とする。
これは見逃し低減を優先するレビュー契約案であり、実装結果や公式の断定ではない。
「GlideAjax由来の積極的証拠がある場合だけ候補」とする代替も人が比較・承認する。
両方を採点者がケースごとに使い分けてはならず、不採用案と理由もカード版に記録する。

必要な証拠：呼び出し式と位置、GlideAjax構築/別名/引数の由来、ローカル定義/上書き、
UI・呼出し契機・結果を使う箇所。未知の呼出し元は独自実装の不存在証明ではない。
承認対象APIは本案ではgetXMLWait。同期らしいAPI全般やサーバー照会全般へ拡大しない。

**確認項目**：`synchronous_ajax_review`（rule_intrinsic）を候補全件でrequiredとする。
受信側が本当にGlideAjaxか、対象UIの制約、同期の必要性、待機の影響、非同期代替と
コールバック後の処理順序を確認する。try/catchや互換分岐でも必須。
受信側不明なら`synchronous_ajax_receiver_unresolved`を制限へ記録する。
独自メソッドと確定してclearなら、この固有項目を生成しない。

**人が決める点**：受信側不明の候補化方針、必要なUIメタデータ、追加する資産種別/APIの範囲。
onSubmit等で送信前の結果が必要な場面について、AU-SRC-002の当該コメントだけでは採否を決められない。
資料に記述がないことを「適用外」や「承認された例外」の証拠にせず、処理順序・代替設計・業務要件を
人が判断する論点として記録する。必要性の申告だけで候補を抑制しない。
