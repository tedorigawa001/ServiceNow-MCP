# BP-5：bounded取得を維持する対象選択の改善案

Version: bp5-target-selection-0.3 / Date: 2026-10-18。
Status: **案A・opt-in方式を実装。新モードの実機E2Eは未実施**。
本書の設計整理後に[実装・合成検証](BEST_PRACTICE_BP5_TARGET_SELECTION_IMPLEMENTATION.md)へ接続した。
PDIへの書き込み、設定変更、ケース作成は範囲外。
公式仕様・固定3条件・次版JSON契約は[具体化資料](BEST_PRACTICE_BP5_TARGET_SELECTION_CONTRACT.md)を参照。

## 1. 問題と目的

[PDI読み取りE2E](E2E_BEST_PRACTICE_REVIEW_2026-10-18.md)では、同じ既存Update Setに
BR/Client Scriptの更新10件と削除5件を別のmetadata照会で確認した。一方、現行ツールの
全種別・sys_id昇順の先頭100件は対象外83件、削除17件で、payload取得・解析は0件だった。
これは対象が存在しないのではなく、**対象外・削除が有限の選択枠を先に消費する問題**である。

目的は、上限を増やさず、要求された規則を評価できる更新候補へ到達しやすくすること。
全Update Setの網羅、全対象の必ずの発見、解析成功100件の保証は目的にしない。
現行の取得順序・JSON契約は[統合設計書](BEST_PRACTICE_BP5_MCP_DESIGN.md)のとおりで、本書で変更済みとはしない。

## 2. 変更しない上限と不変条件

| 境界 | 維持する値・意味 |
|---|---|
| 選択枠 | `max_records`既定20、最大100。成功数ではなくmetadata候補行の予算 |
| metadata一覧 | 初回は最大N+1行。最後の1行はlookaheadで、payloadは取得しない。最終照合も最大N+1行 |
| payload | 選択された最大N行に限り、各1回。1件2MiB、合計8MiB |
| HTTP受信 | 1応答4MiB、全体16MiB。エラー応答・再試行分も同じ全体予算へ加算 |
| HTTP回数 | 全体210試行以内。1要求の再試行は最大1回。最終照合用4試行を予約 |
| 時間 | 開始から60秒。取得・解析50秒、照合55秒、集約・worker終了まで60秒の既存内部期限を維持 |
| 出力 | 指摘最大100件、JSON応答256KiB。本文・原例外を返さない |
| 権限 | 接続先・認証固定、caller ACL内、C方式のmatched permitを一覧より前に必須とする |

N+1は各一覧の論理的な行上限であり、再試行時の再受信を無料にはしない。リリース証拠の
ノード照会等の既存上限も変えない。metadataだけを追加ページで無制限に探すことも禁止する。
受信バイト・HTTP予算・各内部期限は、行数上限に達する前にも処理を止められる。
HTTPの時間制限は、ServiceNow内部のDB処理が同時に停止したことを保証しない。

## 3. 比較と推奨

| 案 | 効果 | 制約・判断 |
|---|---|---|
| A：固定の対象候補フィルターをサーバー側で適用 | 対象外・削除の多くを受信前に除き、同じN+1枠を候補に使う | **初段階の推奨**。厳密な識別は引き続きローカルとXMLで実施 |
| B：更新対象・削除・その他を別照会で優先配分 | 内訳を一部保持しつつ対象を優先できる | 照会・照合・予約試行が増える。各照会N+1では上限増になるため今回は見送る |
| C：ページングして対象が見つかるまで継続 | 後方の対象を探索できる | 総metadata行数・要求数を増やす。固定N+1のままでは単なるページ分割で、根本解消にならない |
| D：上限増加・現在の資産へ代替・対象の並べ替え書き込み | 別の経路で到達する | 上限・payload版・読み取り専用の原則に反するため不採用 |

案Aは全Update Setの一覧機能ではなく、**要求規則向けの候補選択**として提供する。
「先頭100件以外も全部調べた」とは説明しない。候補自体が100件を超える場合は引き続き打ち切る。

## 4. 推奨する選択方針（案A）

1. 入力検証・親取得・C方式の証拠確定は現行順のまま行う。
2. 要求規則から対象種別を内部で決める。AU-BR-001/002はBR、AU-CL-004はClient Script。
3. 親Update Set ID、`action=INSERT_OR_UPDATE`、要求種別に対応する名前接頭辞を、
   サーバー側の固定候補条件として組み合わせる。利用者のquery・table・fieldsは受け付けない。
4. 候補一覧をsys_id昇順、N+1行まで取得。先頭N行が選択枠で、lookaheadから本文を取得しない。
5. 各行の所属・ID・順序・重複・actionと名前の厳密な形を再検証し、適用規則を割り当てる。
6. 選択後のpayload取得・安全なXML抽出・識別照合・worker解析は既存の境界を維持する。
7. 同じ固定条件・順序・上限でmetadataを再取得し、親とともに最終照合する。

### 4.1. 接頭辞は候補抽出であり、識別の証明ではない

BRの厳密な名前は`^sys_script_[a-f0-9]{32}$`、Client Scriptは
`^sys_script_client_[a-f0-9]{32}$`。この正規表現をそのままTable APIで実行できるとは仮定しない。
`sys_script_`接頭辞はClient ScriptやScript Include等も含む。
表示用`type`の文言は、ローカライズや欠落の可能性があるため唯一の選択根拠にしない。

実装前に、固定条件の表現方法、親条件とOR条件の結合、actionの実値、順序・limitの挙動を
公式仕様と合成テストで確認する。名前が重なる既知の対象外接頭辞を除く場合も、除外一覧を
版管理し、対象種別を誤って除外しないことを検証する。未知の接頭辞を含む完全な排除は主張しない。
公式構文を照合した固定クエリ案は具体化資料§2に記載した。実機での解釈・性能は未確認。

候補窓に混入した正規の対象外種別は`not_applicable/asset_type_unsupported`、
壊れた対象名は既存の`identity_mismatch`として記録し、いずれもN枠を消費する。
混入分を補充する追加照会は行わない。フィルターから返るはずのない親・action・候補条件違反は、
APIが条件を守ったものとして黙認せず、収集失敗または観測変化として扱う。既存の固定エラーに
割り当てられない場合は、新しい契約で理由を定義してから実装する。

これにより通常の対象外・削除による枠消費を軽減するが、混入候補による再度の枠消費は残り得る。
候補フィルターの完全性が未確認の状態で「対象の見逃しを解消した」とは主張しない。

### 4.2. 削除と未知のaction

新モードのレビュー選択はINSERT_OR_UPDATEに限定する。DELETEや未知のactionを
「0件」「安全」と判定するのではなく、**選択範囲外・件数未収集**とする。
削除・未知actionを調べるための追加照会は設けない。従来の全種別の有限窓モードは残す。
更新行でactionが取得後に変わった場合は、取得時の版との不一致として解析しない。

## 5. 入出力契約と互換性

現行`bp-mcp-review-0.2`を黙って読み替えない。次版契約（仮称`bp-mcp-review-0.3`）で
次の意味を明示し、既存契約・固定評価セットをそのまま残す。

- 初段階は任意の列挙入力`selection_mode`を追加する案とする。省略時は従来の有限窓、
  明示時だけ`review_targets`。既定値変更は別途承認・リリース通知が必要。
- 選択モード、固定フィルターの版、要求対象種別、action範囲、順序を結果に記録する。
  利用者の自由なフィルター指定は追加しない。
- `metadata_seen`は**そのモードの候補窓で受信した行数**で、Update Set総数や対象総数ではない。
  `selected=min(metadata_seen,N)`、`selected=assets.length`を維持し、各選択行に必ず1結果を返す。
- `truncated`は候補窓のlookaheadでNを超えた意味に限定する。全Update Setの切詰めと
  誤認しないようcoverage scopeを併記し、対象外・削除の除外件数は未取得ならnull相当とする。
- 0件は「caller ACLから見える固定条件の候補0件」であり、資産なし・違反なし・安全ではない。
  公式仕様ではlimitがACL評価前のため、厳密には「その有限一覧から返却された行が0件」。
  0件やN以下の返却でも可視候補の全件取得を保証せず、具体化資料のcoverageで明示する。
- 既存の`analysis_complete`は選択範囲内の機械的完了に限定し、完全なUpdate Setレビューを
  表さないとスキーマ・説明・AI利用例で明記する。候補切詰め、未処理、照合未確認等ならfalse。
  独立品質未承認・根拠承認待ちによるPoCのpartial方針も維持する。
- 窓の外のIDは取得していないため、架空の行別`not_processed`を作らない。
  選択済みで内部期限により未処理の行だけ、既存の`deadline_exceeded`等を付ける。

旧契約を要求する内部利用者・テストへの移行方法、次版の具体的な項目名・列挙値・失敗理由は
実装前にスキーマ案として確定する。新旧の結果形を同じschema_versionで返さない。

## 6. 時間・変更検出・失敗時の扱い

固定フィルターは初回と最終照合で共有する。別種別・別actionを照合したことにしない。
選択範囲に入る行の追加・削除・改名・action変更・版変更・lookaheadの変化を検出したら、
既存どおり暫定結果とし、`analysis_complete=false`。観測間で元に戻った変更、不可視の行、
窓外の変化、DBのトランザクション一貫性は保証しない。`stable_observation`はこの有限候補窓の観測だけを指す。

追加の件数集計・ページ探索・全件検証は行わないため、最終照合の4試行予約は増やさない。
50秒で新規取得・解析を止め、完了済み結果を保持する既存partial方針を維持する。
照合中断はunverified、全体60秒・キャンセル・契約破損は既存の固定エラー方針を維持する。
候補が見つからなくても予算・権限・リリースゲートを緩めず、全種別への自動再照会はしない。

## 7. 実装後に必要な検証

以下の合成検証の実施結果は実装記録を参照。PDI E2Eは未実施。

| 検証 | 合格条件 |
|---|---|
| 対象外100件超の後にBR/Client Script | 新モードで更新候補へ到達。従来モードの挙動は不変 |
| 削除100件超の後に更新対象 | 削除が新モードの選択枠を消費しない。削除件数を捏造しない |
| BRのみ・CLのみ・両方 | 要求規則と対応し、両方でも共有N+1枠。ORで親条件を迂回しない |
| Dictionary/Choice/Script Include・未知接頭辞・壊れた名前 | ローカル分類と除外範囲が仕様どおり。補充・任意payload取得をしない |
| type欠落・異なる表示文言 | typeだけで正規対象を落とさず、XML照合を省略しない |
| 重複・順序違反・別親・フィルター無視 | 収集不正を検出。違反した一覧で安全な完了としない |
| 0件・N件・N+1件・混入だけで枠満了 | カウンター・候補切詰め・coverage・未知の除外件数が整合 |
| 追加・改名・action/版変更・照合失敗 | 同じ選択条件で再照合し、暫定/未確認を正しく返す |
| 受信超過・再試行・50/55/60秒・キャンセル | 同じ予算、partial/固定エラー、worker終了と資源解放を維持 |
| MCP・梱包・既存固定セット | 入力二重検証、本文非露出、出力上限、新旧契約の互換性を確認 |

その後、別途許可された読み取り専用PDI E2Eで、既存Update Setを使い、本文を表示せず
候補取得・payload解析到達数・拒否理由・制限を確認する。データ作成やACL変更で成功させない。
サーバー側条件の性能・実効ACL・取りこぼしは未確認事項として残す。

## 8. 次工程の判断点

案A・初期opt-in方針を採用する。公式仕様照合と次版契約案は具体化資料に記載した。
同資料に基づき合成テストを伴う実装へ接続した。実機E2E・性能は未検証。
厳密なサーバー側対象条件が表現できなくても、粗い候補絞込み＋有限窓としての制限を明示できる場合に限り採用する。
その場合も「100件外の問題を完全解消」とはせず、残る候補枠飽和を別課題として扱う。
