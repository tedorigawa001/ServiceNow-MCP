## 2. 作問の二層と評価単位

| 層 | 件数 | 期待値の位置付け |
|---|---:|---|
| catalog_contract | 24（各規則8） | 宣言済みの付与条件に照らした適合確認 |
| semantic_boundary | 12（各規則4） | 意味上確認したい依存・関連をラベル付け。現カタログの対応範囲を超える拡張課題の確認 |

境界層の不足を、現在の宣言済み契約に対する実装違反と一括で扱わない。
境界の確認要求・制限ラベルも、将来の対応範囲や人による採用承認を決めた仕様ではない。

- workflow: 更新前後での付与差、受信側別名、条件付き抑止、別レコード、未呼出し関数、
  リテラル条件、標準入口＋ループ、再束縛、定数評価・関数間の関連を含む。
- async: async_alwaysを使用し、固定コンテナ、旧入口、複数指摘、before_display、引数束縛、
  独自メソッド、条件欄、フィールド別名、関数間・動的名・分割代入を含む。
- Ajax: コンストラクタ別名＋配列、未解決引数、独自クラス、再束縛、文字列/コメント、
  optional呼び出し、混在受信側、非同期だけの例、動的名・factory戻り値を含む。

全ケースをfilter_condition/item、sys_translated_text/delete_multiple、sys_es_latest_scriptの
ある架空XML封筒に入れる。実PDIのスクリプト本文はコピーしない。
候補を出さないケースも含め、レビュー済み・評価済みを確認してから期待適合とする。

評価単位は「指摘開始行×要求規則×その規則の固有確認コード」。同じ資産で片方だけ
正しく付けた結果を、資産全体の成功として隠さない。NEW-W01では先の更新には付けず、
後の更新だけに付けることを要求する。行番号は合成ケースの照合用で、行ごとに同一規則の
期待指摘は1件まで。複数同一行の指摘位置を厳密評価する契約ではない。

- 候補照合: 開始行で対応付け、余分な候補と候補漏れを別集計。
- 確認項目: 必須コードの付与、不要な付与、他規則のコードを判定。汎用コードだけでは満たさない。
- 付与漏れ: 候補はあるがコードがないものと、候補自体がなくコードも出せなかったものを区別。
- 不要な候補に付いた確認項目も誤付与として数える。limitationsは別に期待集合と照合する。
- 候補を出さない9ケースの成功はケース適合に反映するが、トークン集計のTNを水増ししない。
  必要候補の欠落もTNにはせずnegative_unassessedとして記録する。
- 妥当な拒否はreview_rejections、不正な形式/由来/未知コードはinvalid_outputsとして区別。
  例外メッセージ・未知の拒否理由は結果にコピーしない。

採点器にはケース期待値があるが、検出器に渡すのは既存のpayload入力だけ。
本文・コード抜粋を結果に返さず、ケースID・照合行・集計だけを保存する。
初回測定後に採点器の拒否分類・結果フィールド名を明確化したが、期待値・検出器・
下記の検出/付与集計値は変更していない。

## 4. 誤付与・不足のケース別分類

| ケース | 観測 | 原因・位置付け |
|---|---|---|
| NEW-W09/W10 | 候補あり、workflow確認なし（2件） | falseの変数・論理式。真偽値リテラルだけを認める契約の範囲外 |
| NEW-W11/W12 | 候補あり、workflow確認なし（2件） | 抑止と更新が関数をまたぐ。呼び出し効果・実行順の解析は範囲外 |
| NEW-A09/A10 | 候補とasync確認がない（2件） | 戻り値・引数経由のprevious/フィールド依存 |
| NEW-A11 | 候補とasync確認がない（1件） | 文字列結合のchangesメソッド名 |
| NEW-A12 | 候補とasync確認がない（1件） | 分割代入のprevious別名 |
| NEW-J09/J10 | 候補と同期Ajax確認がない（2件） | 文字列結合・変数による動的なAPI名 |
| NEW-J12 | 不要な候補＋同期Ajax確認（1件） | factoryが返す既知ローカル値を関数間追跡できず、未解決getXMLWaitとして保守的に候補を残す |

NEW-J11では、factoryが本物のGlideAjaxを返す場合も由来は未解決だが、候補と確認を保持し、
synchronous_ajax_receiver_unresolvedを併記した。NEW-J12も同じ制限が出ており、
GlideAjaxと確定した出力ではない。それでも意味上不要な確認なので、誤付与として記録した。
抑制すればNEW-J11側の見逃しに転じ得るため、単純な候補抑制を提案しない。

今回は評価のみ。範囲内の修正が必要な不整合は観測せず、境界の拡張方針は別途設計する。
優先候補は、未解決factory受信側の扱い、限定的な定数/分割代入追跡、関数間解析の扱い。
この測定済みセットへ繰り返し合わせるのではなく、改善後は別の未使用ケースと人の採点も用意する。
