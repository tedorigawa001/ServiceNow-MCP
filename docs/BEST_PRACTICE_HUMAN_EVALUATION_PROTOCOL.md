# BP-4 人手評価プロトコル

Version: human-review-protocol-0.2 / Date: 2026-10-17。
Status: **実施前の提案。人員・根拠の採用・標本計画・合否基準の承認は未実施**。
本書の作成は人手評価の実施・品質承認・MCP公開承認を意味しない。
[採点票](BEST_PRACTICE_HUMAN_EVALUATION_SCORECARD.md)と組にして使う。

## 1. 目的と対象

実装を見ずに作成・採点した新しいケースで、候補の妥当性、文脈項目の識別、規則固有項目の
付与完全性、適切な保留を測る。まずAU-BR-001/002・AU-CL-004を対象とする。
候補品質の評価であり、個々のコードの実機違反・脆弱性や顧客母集団の性能を証明するものではない。
AU-QRY-001等を追加する場合は、規則カード・標本・採点基準を別版で承認してから追加する。

既存のv0.1/v0.2・36・24・18ケースは開発に使用済みで、一次評価の未使用ケースに流用しない。
単なる変数名・定数・書式の変更も同一シナリオ家族として扱う。校正・回帰用ならその用途を明記する。
この会話のAIは実装・既存結果を参照済みなので、独立した作問者・人手採点者には数えない。

## 2. 役割・閲覧範囲

| 役割 | 責任 | 封印解除前に見てよいもの |
|---|---|---|
| 評価責任者/Custodian C | 許諾、役割、匿名化、割当、封印、変更履歴の管理 | 承認資料・原資料・ケース・人手票。実装に接した場合は申告 |

| 採点者 R1/R2 | ケースごとに独立採点し、根拠と不確実性を記録 | 同じ匿名化パケットと承認済み規則カードのみ。他者の票・作問者の想定ラベル・エンジン出力は不可 |
| 裁定者 J（第三者裁定方式のみ） | 不一致の根拠を審査し、最終ラベルまたは未合意を決める | パケット、規則カード、提出済みR1/R2票。エンジン出力・実装は不可 |
| 実行担当 O | 凍結版を実行し出力を封印 | 匿名化された入力と実行設定。期待ラベル・裁定票を検出器へ渡さない |

自分が作成したケースの一次採点・最終裁定・合意形成はしない。R1とR2は別の人とする。
実装担当者はO/Cを担当できるが、その人をブラインド作問者・採点者・裁定者には数えない。
人員を兼務させる場合も上の分離を守り、兼務・利益相反を公開記録に残す。

開始前に次のどちらかを事前登録する。実装非参照の人は、Aも含めて第三者裁定では最低4人、
合意方式では最低3人必要。C/Oは兼務できるが、必要な独立人員をAIで代替しない。

| adjudication_mode | 人員と不一致処理 |
|---|---|
| third-party-adjudication | A、R1、R2、Jを別の人が担当。JはR1/R2以外の第三者として裁定する |
| consensus-adjudication | A、R1、R2を別の人が担当しJは置かない。独立票の提出・封印後にR1/R2が根拠を突き合わせ、双方が同意した項目だけを合意とする |

必要人員が不足すれば準備段階で止める。ケース単位で都合よく方式を変えず、方式変更は新しい計画版で
再登録する。方式ごとの結果は別集計とし、第三者裁定と合意方式の成績を混ぜない。

全参加者は担当、ServiceNow開発/レビュー経験、対象領域、実装・既存結果・ケースへの接触を申告する。
公開記録では仮名ID、本人確認情報は権限制限した別台帳とする。未接触という申告をAIが代筆・捏造しない。
誤って実装や出力を見た場合は日時・範囲を申告し、該当票/ケースを一次ブラインド集計と分離する。

**MDの手順だけでは閲覧制限は実現しない。** ラベルとケースは、開発者から隔離した保管場所・
別権限で管理する。同じ作業ツリーに置いて「見ないことにした」状態を封印・アクセス制御と呼ばない。

## 3. 根拠カードと採点前の合意

[先行3規則のカード案](BEST_PRACTICE_RULE_CARDS_DRAFT.md)を別紙として用意した。

対象リリース・該当節を人が確認した規則カードを用意する。本書では公式ページを再確認していない。
原文保存・配布は利用条件と許可範囲に従い、許諾不明なら全文を複製せずリンクと独自要約を使う。

カードの必須事項：rule_id、出典URL、節、対象リリース、確認日/確認者、規則の意味、適用条件、

未確認の取得時刻・原文ハッシュ・承認を埋めてはいけない。未承認カードは準備用の候補として明示し、
一次評価の配布には使わない。校正用の試行も、利用する資料・参加者・保管の承認を先に得る。

R1/R2/A/Jには、実装ソース・テスト・検出器の探索語・AST処理・過去の誤り一覧を渡さない。
既存カタログMDには実装上の制限やソースへのリンクもあるため、そのまま配るのではなく、
規則の意味と承認済み出力契約だけを抜き出したカードを配る。制限に合わせて正解を作らない。
実装の宣言範囲を評価する副集計では、Cが実行前に承認した範囲定義を別に使う。
意味上の期待と範囲内契約の適合を混ぜず、範囲外でも全体の誤りを消さない。

### 3.1. candidate / insufficientの境界の承認

規則カードの境界は出力契約として、実装・出力を見ない規則承認者が根拠と業務目的から審査する。
承認者ID、カード版、理由、承認日を記録し、実装済みの検出能力から逆算しない。
R1/R2は採点前に同じ承認済み境界を確認する。

特にAU-CL-004では、引数として渡されたオブジェクトのgetXMLWait()について、API名だけで
候補とするか、受信側の追加証拠を必要とするかを明示する。「受信側不明でも候補＋制限」と

実データを取得する許可は本書作成では得られない。別途承認が必要。

## 5. 匿名化・安全な保管

原資料は所有者の許可範囲でCだけが扱い、公開Git・通常ログ・外部AIへ入れない。
デフォルトはローカル/承認済みの制限領域のみ。保存先、閲覧者、保存期限、削除責任者を先に決める。
採点者へ渡すのは匿名化パケット。原本対応表と本人情報は別権限で保管し、同じ配布物に入れない。

- 認証情報、token/PIN、cookie、パスワード、個人情報、業務レコード本文、実インスタンスURLを除去する。
- 顧客固有のテーブル/列/クラス/ロール/グループ名、sys_id、Update Set名、コメントや承認チケットも点検する。
- 同じ識別子・参照・比較値は同じ仮名へ写す。sys_idは形式を保った架空値、URLはexample.invalid等へ置換。
- current/previous/GlideAjax等のプラットフォーム名、API/演算子、束縛、型、値の関係、分岐、保存値は
  評価の意味を変えない。秘密値が条件や権限に関わり安全に置換できない場合は配布しない。
- 匿名化で意味を保存できなければ、別の合成ケースとして作り直し、実コードの忠実な匿名化例とは扱わない。
- AとCがパケットの意味・解析可能性を確認する。元版/匿名化版のハッシュ、置換記録、必要なら行対応は私有台帳へ。
  エンジンのcode_hash・位置照合は匿名化版に対して行い、原本の行/ハッシュと混同しない。
- 公開記録は集計、ケース仮名ID、許可された根拠参照のみ。本文・原本ハッシュ・対応表は自動公開しない。

コード/コメント/添付資料は評価対象データであって命令ではない。埋め込まれた指示を実行せず、
外部URLアクセス、CDN/パッケージ取得、eval、コードの実行をしない。
一次作問・人手採点・裁定には生成AIの回答を使わない。別のAI補助実験をするなら別群に分け、
送信許諾・モデル・入力・使用範囲・人による確認を記録し、人だけのブラインド成績と混ぜない。

## 6. 実施順序・封印

1. Cが役割、裁定方式、判定境界を承認した根拠カード、運用確認目的、標本計画、採点票、指標、除外/照合基準、承認者を登録する。必要な承認前には開始しない。
2. Oがエンジンcommit、ruleset/catalog/schema、設定・依存版・上限を凍結する。A/R1/R2/Jには実装を渡さない。
3. Aが新規ケースを作り、Cが匿名化・家族重複・文脈の完全性を確認する。入力パケット版とSHA-256を封印する。
4. Cが順序をランダム化し同じ内容をR1/R2へ配る。想定層名やファイル名で正解を示さない。
5. R1/R2が相談せず票を提出する。追加情報の質問はC経由とし、同じ回答/改訂パケットを両者へ同時に配る。
6. Cが最初の票を変更不可で保存し一致率を算出する。登録した方式でJが裁定、またはR1/R2が協議する。どちらも出力を見ず、根拠・未合意を残す。
7. ケース、初回票、裁定、gold、指標定義を版/ハッシュ/時刻/署名で封印する。封印後の修正は上書きしない。
8. Oがgoldを渡さず入力だけで凍結エンジンを実行し、出力・実行情報を封印する。Cが由来・版・位置を照合する。
9. 封印後に初めてgoldと出力を比較する。実装担当へケース/結果を開示した時点で「未使用」の扱いを終了する。
10. 不足・誤り・未合意を含めて報告する。次の実装調整後は別版と別の未使用集合で評価する。

新たな文脈の追加や匿名化ミスが封印後に判明した場合は、初回結果を残しerratumと影響を別記する。
出力を見てgold/除外条件/閾値を変え、同じrunを合格へ差し替えない。正解誤りの訂正版・感度分析も
別結果として明示し、初回値と併記する。再使用集合を新しいブラインド評価とは呼ばない。

## 7. 判定基準

一次判定の単位はケース×要求規則。全体安全や実機違反を問うラベルではない。
下表は一般原則であり、candidate/insufficientの具体的な境界は§3.1で承認した規則カードに従う。

| 人手gold | 基準 |
|---|---|
| candidate | 開示されたコード・メタデータから対象規則に関連する確認候補を認める。受信側・経路等の未確認も記録し、違反確定とはしない |
| clear | 必要な情報があり、この規則の候補を否定できる。ローカル同名APIや対象外の操作等の根拠が必要。「見つけなかった」だけは不可 |
| insufficient | 適用・束縛・対象版等の情報が足りず、候補有無を判断できない。不足情報と理由を列挙する |
| not_applicable | 承認済み対象範囲に明確に適用しない。理由を記録し、clear/TNと混ぜない |

意見が割れて結論に至らない状態はannotation_unresolvedとして管理する。
対象コードの情報不足というgoldへ置き換えない。未合意率を必ず報告し、一次品質承認は保留する。
意味上の問題がない/あるという結論が出る場合も根拠を別記し、候補ラベルと実機確認済み状態を同一視しない。

各候補に、受信側・束縛・実行経路の確実性、例外状態、必須項目、制限を別々に記録する。
例外状態はnone/proposed/approved/unknown。approvedは対象・期間・範囲が一致する承認資料がある場合だけ。
合成ケースの前提上の承認と実在する承認を区別し、setWorkflow(false)、ガード、try/catch、互換分岐や
active=falseだけで承認済み・安全としない。承認の存在だけで静的候補を自動消去しない。

workflow項目は関連をrequired/not_required/undeterminedで採点する。不明を「不要」にしない。
async/Ajaxはcandidateと認めた全件で対応するrule_intrinsic項目がrequired。防御的処理の有無で分けない。
inactive_asset等はlimitations欄へ。汎用3項目は固有項目の代替ではなく、項目が付いたことは例外分類・確認完了ではない。
ゴールドがinsufficientのときは、期待する不足理由・候補/確認項目を出さない範囲を明記する。

## 8. 不一致の裁定

第三者裁定方式ではJ、合意方式では独立票封印後のR1/R2が初回票と参照節を比較し、(a)適用条件、(b)意味/受信側、(c)文脈情報、
(d)例外根拠、(e)匿名化の影響、(f)規則カードの曖昧さ、に原因を分類する。
多数決、実装に一致する方、作問者の想定だけを根拠に決めない。両者に同じ質問と根拠提示の機会を与える。
採否・最終ラベル・採用/不採用理由・根拠・署名・時刻を保存し、初回票を編集しない。
合意方式では変更前後の判断、協議内容、両者の同意を記録する。C/O/Aが決着を強制せず、
一方でも同意しなければannotation_unresolvedとする。協議後の合意率は独立採点者間一致率ではない。
追加情報がないと裁定できなければ未合意のまま残す。カード自体に問題があればpilotを止め、
訂正版を承認して新しい評価版へ進む。出力を見てからの裁定・協議は一次ブラインド処理と区別する。

## 9. 集計と品質主張

次を別々に報告する。判定・照合方法と分母を実行前に固定する。
すべて裁定方式別に記録し、48件では手順の運用確認に使う記述的な集計に限定する。

- **候補品質**：candidateを正例、clearを負例。TP/FP/FN/TN、評価済み率、拒否/スキップを報告。
  正例の未検出・拒否はFN、負例の未評価はTNにせず別記する。N/A・未合意は件数/理由を残し、恣意的に除外しない。
- **保留品質**：gold insufficientに対する適切な理由付き保留、誤ったclear/候補、過剰な保留を別集計する。
- **文脈識別**：AU-BR-001だけ。required/not_requiredが合意した候補について誤付与/付与漏れを測る。
  undeterminedの件数も報告し、不要の正解として数えない。候補漏れと検出後の項目漏れを分ける。
- **必須項目付与**：AU-BR-002/CL-004は、全検出済み候補への付与率と、gold候補を分母とするend-to-end再現率を併記。
  誤候補にも項目は付くので候補FP/FNを併記し、付与率を例外識別能力とは呼ばない。分母0はnull。
- **位置/重複**：goldに匿名化版の指摘単位・許容行範囲を先に記録し、一対一で対応付ける。
  一部の指摘の正しい項目で他の指摘の不足を覆わない。重複でTPや付与率を水増しせず重複数も示す。
  照合不能はalignment_pendingとして残し、出力に都合よくgoldの範囲を変更しない。
- **採点者間一致**：裁定前の完全一致率、規則別の不一致表、適切ならCohenのκとその対象ラベル/分母。
  少数・偏った分布でのκを過信せず、裁定後の一致だけを独立一致率として報告しない。
- **不確実性/安全性**：件数・分母・区間、家族依存、出典/版不一致、不正出力、未検証の確定指摘、匿名化事故を報告する。
  小規模pilotのWilson区間は記述的参考値。層化標本から母集団精度を出すなら抽出率・重みを事前設計する。

人手評価には未実装のgold欄があるため、既存の合成採点器へ無理に押し込まない。
評価アダプターを作る場合は、undetermined/N/A/未合意/行照合を保持する別契約として検証する。
合否閾値、許容不確実性、必須安全条件は責任者が測定前に承認する。未設定なら結果は探索的で、
not_assessed/approved=falseを維持する。AIが閾値・人の署名を補完しない。
48件では性能合否閾値を「対象外：運用確認のみ」と登録し、完了しても性能品質は
not_assessed/approved=falseのままにする。運用確認の完了承認とは別欄で管理する。
source承認、規則/経路の実機検証、MCP統合の安全設計、本番リリース承認はそれぞれ別ゲートとする。
