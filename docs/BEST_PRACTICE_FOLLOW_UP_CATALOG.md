# レビュー確認項目の共通語彙（PoC実装版）

Version: bp-followups-0.4。2026-10-17。方針1を維持し、限定的な定数評価を付与条件に追加。
人による採点・根拠資料の採用承認・本番品質の承認は別途必要。
後続規則の追補profileを含む現行語彙は12項目。AU-CL-002の`client_lookup_necessity_review`は[Client Script照会候補](BEST_PRACTICE_CLIENT_LOOKUPS.md)、AU-CL-008の`onchange_loading_intent_review`は[onChange読込時候補](BEST_PRACTICE_ONCHANGE_LOADING.md)を参照。固定3規則用の版・評価履歴は変更しない。

正本は[src/review/follow-up-catalog.ts](../src/review/follow-up-catalog.ts)。
採点器だけのローカル語彙を製品仕様に昇格させず、まず意味・適用規則・付与文脈・
その項目が証明しないことを共通カタログとして定義する。
これは公式ServiceNow APIの列挙値ではなく、このPoCの追跡確認用語彙。
根拠となる推奨・例外は[Australia台帳](BEST_PRACTICE_REGISTER_AUSTRALIA.md)の該当節を参照する。

## 型と互換性

初版FOLLOW_UP_CODESは6項目の列挙、FollowUpCodeはそのTypeScript型、followUpCodeSchemaは
Zod列挙型。結果契約モジュールからも型・スキーマを再エクスポートする。
適用規則はisFollowUpApplicableで照合でき、未知の規則は拒否する。

bp-review-0.1のrequired_follow_upは、過去の自然文を含む結果との互換性を維持するため、
自由記述のままにする。既存のrequired_follow_upのJSON Schema定義・保存結果は変更しない。
この段階では「全既存結果が列挙値だけに制限された」とは主張しない。
将来、結果のコード欄を厳格化する際は、表示用説明とコードを分離するか、結果契約を
別版にして移行する。既存の自由記述を黙って列挙型に置き換えない。

## 語彙

| コード | 適用 | 意味・付与する文脈 |
|---|---|---|
| source_approval | 全規則・汎用 | 根拠がcandidate/未承認の場合に、適用範囲と採用可否の人による確認を求める |
| binding_and_reachability | 全規則・汎用 | 構文候補の変数束縛・受信側・実行経路を解決できていない場合の確認 |
| exceptions_and_business_intent | 全規則・汎用 | 業務意図や例外条件・承認の有無が未確認の場合の確認 |
| workflow_suppression_review | AU-BR-001・文脈固有 | 同一関数内でcurrent由来の1引数setWorkflowが更新候補より先行し、引数が限定的定数評価でfalseと確定した場合に、抑止理由・必要性・承認範囲・副作用を確認 |
| async_dependency_review | AU-BR-002・rule_intrinsic | AU-BR-002候補の全件で、依存・フォールバック・互換処理を確認。ガードや例外処理の有無に依存しない |
| synchronous_ajax_review | AU-CL-004・rule_intrinsic | AU-CL-004候補の全件で、受信側・UI制約・同期の必要性・非同期代替を確認。互換分岐やtry/catchの有無に依存しない |

汎用項目だけで文脈依存・規則固有の項目を満たしたことにはしない。
workflow_suppression_reviewだけがcontext_specific。後者2項目はrule_intrinsicであり、
確認項目が付いていることから「例外に該当」と分類してはいけない。
setWorkflowという語があるだけでworkflow項目を付けない。受信側・更新との順序/分岐の
対応が未解決なら、その制約を併記する。条件欄のchanges系はasync本文と混同しない。
同名メソッドをGlideAjaxと断定しない。具体的項目の付与も違反・経路・例外の確認完了を
意味せず、verification_statusを昇格させない。

inactive_assetは確認項目コードではなくlimitationsの文脈値として別定義する。
レビュー対象版のactive=falseを確認した場合に付け、未知値や別時点の値から推測しない。
非アクティブだからと候補を一律抑制したり、安全性を保証したりしない。

## 初回の実装順序と採点器の位置付け（0.1の記録）

1. 今回の共通語彙・付与条件をレビューする。
2. 文脈検出と結び付いた出力処理を実装する。字句スコープ/受信側解析が未完ならその限界を明示する。
3. 正例だけでなく同名API・無関係な抑止・条件欄等で項目を誤付与しないテストを実施する。
4. 固定済みv0.2で開発用再評価し、改修に使っていないケースと人の採点で別途検証する。

初回、v0.2の規則固有コードと列挙型は共通カタログ参照へ変更したが、許容集合・採点条件は
変更していない。v0.2の72ケース・保存結果・検出器も変更しない。
F系12件の不足は、現検出器が新しい具体的項目を出さないために生じる出力契約の実装差分であり、
候補検出の取りこぼしではない。語彙の存在だけを理由に全候補へ一括追加して合格させない。

- 現検出器が汎用項目だけを返すことと、共通化後もv0.2の固定結果が完全一致すること。

## 0.2のレビュー結論と出力実装（履歴）

6コードの意味・規則対応は維持し、workflowの曖昧だった「関連し得る」を上表の構文条件に
具体化した。異なる関数・既知のローカル受信側・単なる文字列/コメント・更新後だけの抑止は
付与しない。同じ関数の別名と固定プロパティ/添字経由は既存の受信側追跡を使う。
分岐の両側や途中でsetWorkflow(true)に戻す形は、抑止効果の証拠とはせず確認対象として残す。
`workflow_suppression_relation_not_verified`を結果のlimitationsに併記する。

asyncはガード/try/catchの有無にかかわらず、実際の依存候補に確認を付ける。
条件欄だけのchanges、既知のローカル受信側、非async文脈からは生成しない。
同期Ajax候補も実際の検出に結び付け、受信側未解決なら
`synchronous_ajax_receiver_unresolved`を併記する。全規則へ固有コードを一括追加しない。

上記2つとinactive_assetは確認項目コードではなく制限。結果全体のlimitationsであり、
各指摘の確認項目はrequired_follow_upに出す。コード・意味・付与条件・証明しない事項の正本は
カタログに置き、生成時も未知規則/別規則の固有コードを除外する。

当時のrulesetはbp3-0.3、語彙はbp-followups-0.2。結果契約bp-review-0.1の自由記述互換は維持し、
旧結果も引き続き受け入れる。固定v0.2の許容集合・採点条件は変えない。
検出器には期待値を渡さず、[別保存した再評価記録](BEST_PRACTICE_FOLLOW_UP_REEVALUATION.md)で
12契約改善・契約退行0件を確認する。PDI操作・外部送信は実施しない。

## 0.3の方針と評価の分離（継続する方針）

AU-BR-001はworkflow抑止との関連を識別する文脈依存項目。
AU-BR-002/CL-004は通常の問題候補にも防御的処理のある候補にも必須の規則固有項目とする。
出力生成関数は「検出した候補」に対して呼び、規則固有項目は付与時の文脈マーカーに依存させない。
候補自体がなければ項目だけは生成しない。未知規則・他規則コードは従来どおり除外する。
旧legacy/scopedプロファイルは汎用項目のみを返す互換経路を維持する。
ruleset bp3-0.3・結果契約はそのままで、実際の検出候補へのコード出力は既存評価内で変わらない。

評価は以下の2軸を混ぜない。

1. 文脈識別：AU-BR-001だけ。必要/不要の付け分け、誤付与、取りこぼしを評価。
2. 必須項目の付与完全性：AU-BR-002/CL-004。検出済み全候補への付与率を評価。
   候補検出を含むend-to-end再現率、候補FP/FN、他規則コードを併記する。
   候補を誤検出しても規則固有項目の付与は完全になり得るため、完全性を精度・例外識別能力としない。

v0.2の18/18は要求項目の充足だけを意味する。改善12件のうち、文脈依存の付与改善4件と
規則固有項目追加8件を分ける。例外文脈を12件識別した結果ではない。
candidate_with_followupという旧採点ラベルも、人による例外承認を表さない。
将来例外を分類する場合は、確認項目の有無とは別の証拠付き契約が必要。

固定v0.2と36ケース・既存JSONは変更せず、[次版24ケースの検証](BEST_PRACTICE_FOLLOW_UP_POLICY_EVALUATION.md)で
通常候補にも固有項目を要求する。既存CLIは履歴メタデータ0.2を再現し、新CLIだけが現在の
カタログ版0.3と分離指標を記録する。過去の結果JSONを現在の意味に書き換えない。

## 0.4の限定的定数評価

新ruleset bp3-0.4では、文字列/真偽値リテラル、初期化済みで書込のない同一関数内のconst、
文字列同士の`+`、真偽値の`!`/`&&`/`||`、既知プリミティブの`===`/`!==`、既知真偽値条件の
三項式だけを評価する。API名・固定コンテナのキーとworkflowのfalse判定に使う。
constの初期化順・シャドーイング・代入先の束縛を確認し、未知値は推測しない。

let/var、関数呼び出し、プロパティからの値取得、暗黙の型変換、数値演算、テンプレート文字列、
分割代入や関数をまたぐ定数伝播は対象外。キー不明のコンテナ・spreadの不確実性を残し、
解決したキーを理由に未解決のAjax受信側をローカルと断定しない。
workflowの関連未確認という制約、rule_intrinsicの分類は変えない。

旧カタログ0.3までのリテラル限定条件による結果を上書きせず、
[固定再評価と新規18ケースの記録](BEST_PRACTICE_CONSTANT_EVALUATION.md)を別保存する。
カタログ・rulesetの改版で対応範囲を明示するが、既存の固定ケースのbasisラベルは移動しない。
