`9edbe42d8546f898640c55f86c219ed71d1159a540aa06870090a7f327d988df`。

problem/no_problem/exception/insufficient各18件、各規則×カテゴリは6件。
対象規則はAU-BR-001/002・AU-CL-004、単位はケース×要求規則で出現数ではない。
新規のswitch・短絡式・戻り値/配列/オブジェクト経由・let/アロー/catch/クラスの束縛・
複数制限の組合せ・重複本文/識別不一致等のシナリオを含む。
既存のコード断片のコピーではないが、同じ規則・概念や関連する変形も含む。
作問者は実装とv0.1結果を参照済みであり、ブラインドholdoutや独立同分布の標本ではない。
PDIコードは使わず、人による採点承認も未実施。サーバーホストメソッド.callを前提とする

### 期待結果と情報不足

| 期待結果 | 満たすべき出力 |
|---|---|
| candidate | 対象規則の候補を返す。追加の適切な追跡確認があっても候補有無の契約は満たす |
| clear | 対象規則を評価済みで候補なし。拒否/スキップはclearにしない |
| candidate_with_followup | 候補と、そのケースで宣言した必要な追跡確認/制限をすべて返す |

insufficientは3分類に含めず、別軸の理由付き保留とする。候補0件、正しい単一理由、
completedを主張しないことが必要。リリース不明/不一致は引き続き候補を出さない。
ケースの期待ラベル・rationale・確認項目は採点器だけが読み、検出器の入力には渡さない。
検出器は今の取得メタデータとpayloadだけを受け取り、架空の承認を推測しない。

Zodのstrict契約で、72件の件数・カテゴリ/規則の層化・ID一意性・期待結果・
必要確認項目・制限を検証する。カテゴリと期待結果は固定対応、別規則の確認項目は拒否する。
case本文・ID・ラベルの変更は別版とし、初回結果に合わせて修正しない。

### 追跡確認の意味と採点

| 規則/文脈 | 評価で要求するトークン | 意味 |
|---|---|---|
| workflow抑止付きBR | required_follow_up: workflow_suppression_review | 抑止理由・承認範囲・必要性と副作用を確認。抑止だけで承認しない |
| asyncの防御的/互換処理 | required_follow_up: async_dependency_review | previous/変更判定への依存とフォールバック・実行条件を確認 |
| 同期Ajaxの互換用途 | required_follow_up: synchronous_ajax_review | UI制約・同期の必要性・非同期代替を確認 |
| 非アクティブ資産 | limitations: inactive_asset | 静的候補を保持し、実行中とは断定しない |
| 追加の束縛/到達性確認 | required_follow_up: binding_and_reachability | 上記の具体的文脈と組み合わせる補助項目。これだけでは適合にしない |

汎用のexceptions_and_business_intentやsource_approvalだけでは具体的な確認を満たさない。
必要な集合の包含を対象規則の各指摘について検査する。複数指摘の一部だけに確認項目を
付けて全体を合格させない。非アクティブとworkflow等の両方を要求するケースもある。
トークンは意味を持つ評価用語彙であり、文言の妥当性や実際の確認実施を証明しない。
この作業で検出器に新しい確認トークンを追加してスコアを合わせることはしない。

actualの分類はgoldを見ずに決める。候補ありで、対象規則の具体的確認トークンまたは
inactive_assetが全指摘をカバーすればcandidate_with_followup、それ以外はcandidate。
一部の確認を持つだけでactual分類がfollowupになっても、必要集合が不足なら契約不適合。
レビューJSONのverification_statusやschema_versionは変更しない。

### 指標と安全性

候補有無の二値評価ではcandidateとcandidate_with_followupを正例36件、clearを負例18件とする。
情報不足18件は二値指標に混ぜない。正例の拒否/スキップはFN、負例の未評価はTNにせず分離する。

別に、判定可能54件の契約充足率、厳密な3分類一致率、混同行列、followup全期待ケースでの
充足率と候補検出済みケースだけの充足率、情報不足の適切な保留率を報告する。
厳密な3分類一致はラベル一致に加えて必要集合の充足を要求する。
candidateに追加確認が付いた場合、契約は満たしても厳密分類一致には数えない。

件数・分母・点推定と95% Wilson区間を併記する。分母0はnull。
Wilson区間はz=1.959963984540054による参考値であり、合成・関連ケースを
母集団の二項標本と見なす95%保証ではない。v0.1と単純に数値比較して改善を主張しない。

出力の構造・根拠・カバレッジは既存のreviewResultSchemaで検証し、対象資産・Update XML・
payload/codeハッシュ・取得メタデータ・コード位置の上限も照合する。
不正な出力や採点途中の例外はinvalid_outputとして失敗を残す。
未検証の確定指摘、無効な結果、情報不足の不適切な処理があれば安全チェック不合格。

**この版は探索的評価で、80%/90%のリリース品質ゲートは設けない。**
release_quality_gateはnot_assessed / approved=falseを常に記録する。
人によるラベル確認・標本設計・許容不確実性が未完了のため、合成オラクルが全契約を
満たしてもリリース承認にはならない。contract_suite_passedはケース契約と安全性だけの指標。

入力や実行の異常はexit 1。結果はケースID・件数・欠けている確認項目等のみで、本文を返さない。
CLI・採点器・ケースはローカルPoCであり、MCP・npm配布・PDI操作・外部送信には接続しない。

## レビュー指摘を踏まえた次段階の範囲（2026-10-17）

### 確認項目の共通語彙を先に定義

[確認項目の共通カタログ](BEST_PRACTICE_FOLLOW_UP_CATALOG.md)に、既存汎用3項目と
文脈固有3項目の列挙型・意味・適用規則・付与条件・証明しないことを定義した。
v0.2採点器はその共通定義を参照するが、採点の許容集合と条件は変更しない。
語彙は提案版・レビュー未承認であり、採点器の期待を未審査のまま検出器の仕様にしない。
結果契約0.1の自由記述を即座に破壊的変更せず、型付きコードと既存の自然文の移行は別版で扱う。
検出器からの具体的項目の出力は、文脈検出に結び付けた実装・テストより後とする。

### 実データ構造を模した封筒の回帰テスト

v0.2の固定入力は最小の本体レコードだけであり、その評価だけではPDI相当の封筒構造を通らない。
そこで固定ケース・採点器の入力構築・保存結果を変更せず、別の回帰テストで72入力を包み直す。

- BR本体にfilter_conditionのitemを追加する。
- sys_translated_text（delete_multiple）とsys_es_latest_scriptを本体と並べる。
- 補助レコードを本体の前/後に置いた2通り、計144パターンを確認する。
- 補助レコードのscript/when/sys_idは本体に混ぜない。出力・コードハッシュ・位置・拒否理由は
  最小封筒と一致し、payload_hashだけは包んだ実payloadに対応して変わることを確認する。

これは架空コードによる回帰検証であり、独立ケースを144件増やしたことにも、
v0.2の品質スコアを更新したことにもならない。PDI本文のコピーや再アクセスはしない。

### 改良範囲の分離と事前に固定する条件付き到達点

ケースIDはすべてV2-接頭辞。次の対応は未実装であり、実測改善を示すものではない。

| 区分 | ケース | 今回想定する改良範囲 |
|---|---|---|
| オブジェクト/配列に保存したレコード別名 | P04/P05/P09/P11 | 関数内の固定プロパティ/定数添字の限定的追跡。一般的なヒープ解析ではない |
| 引数や戻り値を通すレコード別名 | P03/P06/P10/P12 | 関数をまたぐ解析が必要。次の限定的改良からは除外 |
| 動的メソッド名/間接実行 | P17/P18 | P17はparts.join等の定数評価、P18は戻り値・メソッド別名とapplyの呼出しモデルも必要。定数評価だけで両方直るとはしない。範囲外 |
| let・引数・catchの束縛 | C02/C03/C04/C08 | 字句スコープ解決で対応を目指す |
| 独自クラス/オブジェクトの同名メソッド | C07/C11/C14/C16 | 受信側の束縛・由来を追跡し、currentのフィールドのchanges系等と区別する |
| 文脈固有の確認項目不足 | F系12件 | 検出精度とは別の出力契約。カタログ承認と文脈検出に結び付く出力実装が必要 |

字句スコープ・受信側の由来・上記4件の限定的別名追跡がすべて想定どおり改善し、
新たな退行がないと仮定すると、FP8→0、FN10→6、TP26→30、TN10→18。
候補適合率30/30=100%、再現率30/36≒83.3%が、このケース集合での条件付き到達点になる。
これは確約・性能予測・品質承認ではない。関数間や動的実行まで直したように報告しない。
followup充足6/18はこの解析改良だけでは変わらず、判定可能ケースの契約充足も最大36/54の試算。
改善後は区分ごとのIDで差分を説明し、想定外の改善・退行も分けて記録する。
